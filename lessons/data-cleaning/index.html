Data Cleaning and Preparation

Every dataset arrives with a history you did not witness. This lesson is about deciding what to change — and being able to say why, six months later, to someone who was not there.

Why this matters

The decision nobody wrote down

A result gets published. Two years later someone tries to reproduce it and gets a different number. The analysis code is fine. The statistics are fine. The difference is upstream: somebody dropped rows, and no record survives of which rows, or why.

This is not a rare failure. It is the ordinary consequence of treating cleaning as tidying-up — a chore you do before the real work rather than a sequence of judgments the real work depends on. Every deletion, every fill, every type conversion is a claim about what the data means. Claims need reasons.

For the next fifteen minutes you will work on 150 rows of the Iris dataset — small enough to see all of, real enough to surprise you. Everything you decide gets written into a report you can read at the end.

Step 02 · a rule you can state

Column names are code, not labels

Trim the whitespace, lowercase everything, replace spaces with underscores, drop the parentheses. It is a small rule and it is worth writing down, because the next person to read your script needs to know it was applied deliberately.

python
df.columns = [
    str(c)
    .strip()
    .lower()
    .replace(" ", "_")
    .replace("(", "")
    .replace(")", "")
    for c in df.columns
]

Adapted from DS-L03 · Standardize Column Names

  • Sepal Length→—
  • Sepal·Width·→—
  • Petal Length→—
  • ·Petal·Width→—
  • Species→—

This rule is adequate for the known Iris columns and is not a complete solution. Real datasets contain punctuation, repeated underscores, non-English characters, and names that collide once standardized. A production workflow checks for those cases explicitly.

Step 04 · order matters

Convert types before you handle missing values

A numeric column can arrive as text because one cell says “unknown”. errors="coerce" turns anything unparseable into NaN — which makes the invalid value visible, and creates missing data that was not there before.

python
for c in expected_numeric_cols:
    before_missing = int(df[c].isna().sum())
    converted = pd.to_numeric(df[c], errors="coerce")
    after_missing = int(converted.isna().sum())

    if after_missing > before_missing:
        print(f"{c}: conversion created "
              f"{after_missing - before_missing} missing value(s)")

    df[c] = converted

Adapted from DS-L03 · Detect and Convert Numeric-Like Columns

That reported count is the whole point. Conversion runs first so that any missingness it creates is visible to the step that handles missingness — and is attributable to the conversion rather than to the source data.

Step 06 · confirm

Assert the conditions you said the output must meet

Assertions stop a workflow when a required condition fails. The skill is choosing conditions justified by this dataset and this downstream purpose — not conditions you assume every dataset satisfies.

  1. ·

    No missing values remain

    assert final_missing == 0
  2. ·

    All four measurement columns present

    assert set(expected_numeric_cols).issubset(df.columns)
  3. ·

    All measurement columns are numeric

    assert all(is_numeric_dtype(df[c]) for c in expected_numeric_cols)
